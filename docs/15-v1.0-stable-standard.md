# ElectroDSL 1.0 stable standard

ElectroDSL 1.0 is the first stable language and reference-toolchain contract.

## Compatibility guarantees

- A valid 1.0 document remains valid throughout the 1.x series unless it relies on a documented defect.
- New 1.x syntax is additive. Existing syntax is not repurposed.
- Stable JSON schema identifiers are immutable. Incompatible schema changes require a new major version.
- Diagnostic codes retain their meaning throughout 1.x. New diagnostics may be added.
- The canonical IR keeps electrical meaning separate from presentation preferences.
- The reference toolchain continues to read language versions 0.1 through 0.9 via its legacy compatibility layer.

## Stable public API

`@electrodsl/core` is the supported programmatic entry point. It exposes version constants, compatibility checks, parsing, formatting, validation, SVG compilation, connectivity analysis, production reports, and canonical IR serialization.

```ts
import { parseDocument, validateDocument, compileSvg } from "@electrodsl/core";

const document = parseDocument(source);
const quality = validateDocument(document, symbolProvider);
const svg = compileSvg(source);
```

Deep imports into implementation packages are not part of the stable public API contract.

## Command-line contract

```powershell
node packages/cli/dist/index.js version --json
node packages/cli/dist/index.js compatibility 0.4 --json
node packages/cli/dist/index.js project check examples/project-v1.0 --format sarif
node packages/cli/dist/index.js project build examples/project-v1.0
node packages/cli/dist/index.js project verify examples/project-v1.0
```

Exit code zero means the requested operation completed without blocking errors. Quality warnings do not cause a failure.

## Stable schemas

The 1.0 project, canonical IR, production report, connectivity, quality, and artifact schemas are published in `schemas/`. SARIF 2.1 and JUnit XML remain the standard CI interchange formats.

## Versioning and governance

The toolchain follows semantic versioning. Language and schema proposals follow the public RFC process. Breaking changes require an RFC, a new major version, migration guidance, and new conformance fixtures.
